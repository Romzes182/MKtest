# Правила работы с MKtest

Инструкции действуют для всего репозитория. Работай как Senior-разработчик и
архитектор ПО: анализ → причина → минимальные изменения → проверка → отчёт.
Отвечай пользователю на русском; в инструкциях для Visual Studio учитывай русский
интерфейс. При запросе готового решения предоставляй полный код без ненужной теории.

## Контекст проекта

- `MKtest.sln` содержит приложение `MKtest` и тесты `MKtest.Tests`.
- Приложение: C#, WinForms, `net48`, Windows 7 SP1 x64 и новее, включены nullable и implicit usings.
  Зависимости: `SSH.NET` 2026.0.0, `System.Text.Json` и `System.Threading.Channels` 9.0.22.
  `Compatibility/` содержит адаптацию API .NET Framework; сохраняй отмену сетевых операций.
- Тесты: `net48`, MSTest; версии пакетов заданы в
  `MKtest.Tests/MKtest.Tests.csproj`.
- `MKtest/Program.cs` — точка входа с STA; `MainForm.cs` связывает компоненты,
  `MainForm.Designer.cs` и `MainForm.resx` относятся к форме и её ресурсам.
- `MKtest/UI/` — контроллеры интерфейса, раскладка и отображение журналов.
- `MKtest/Managers/` — координация операций; `Managers/Settings/` — секции настроек.
- `MKtest/Services/` — протоколы, SSH, веб-сервер, сценарии и инфраструктура.
- `MKtest/Configs/` — модели конфигурации; `Services/ConfigService.cs` — её хранение.
- `MKtest/Checklists/` — каталог, выполнение, импорт, печать и интерфейс чек-листов.
- `DemoScenarios/`, `JsonTemplates/`, `Routes/` внутри `MKtest/` — данные приложения;
  правила копирования в выходной каталог находятся в `MKtest.csproj`.
- `MKtest.Setup/` — Visual Studio Installer Projects (`.vdproj`), MSI для текущего
  пользователя, Windows x64. Профиль `Setup-win-x64.pubxml` публикует сборку .NET Framework 4.8.
  MSI проверяет SP1 и Framework, setup.exe предлагает установку Framework с сайта Microsoft.
  Для установщика используется конфигурация решения `Setup | Any CPU`;
  Debug/Release не требуют расширения Installer Projects.
  Правила сборки и обновления версии описаны в `MKtest.Setup/README.md`.

Перед работой сверяй этот контекст с актуальными файлами: источником истины служит
код текущей ветки, а не предположения о версиях или архитектуре.

## Анализ и минимальные изменения

1. До редактирования проверь текущую ветку, `git status`, локальные инструкции,
   архитектуру, зависимости, связанные файлы, обработчики и тесты. Сохраняй чужие
   незакоммиченные изменения.
2. Для ошибки сначала установи причину по коду, воспроизведению или журналам.
   Отделяй подтверждённые факты от гипотез. Затем делай минимальное исправление.
3. Не удаляй и не переписывай работающий функционал без разрешения пользователя.
   Не заменяй полноценный код заглушками или имитациями.
4. Не меняй интерфейс, настройки, протоколы, форматы данных и структуру проекта
   без необходимости для текущей задачи. Избегай попутного рефакторинга,
   массового форматирования и переименований.
5. Сохраняй совместимость с целевой версией .NET, библиотеками и оборудованием.
   Не обновляй зависимости и TargetFramework без необходимости для задачи.
6. Не выдумывай API, классы, методы или результаты проверок. Проверяй наличие и
   сигнатуры по исходникам, установленным пакетам или документации нужной версии.
7. Пиши понятный поддерживаемый код, разумно применяя SOLID, DRY и KISS.
   Используй существующие границы UI, менеджеров и сервисов; не добавляй
   абстракции без практической необходимости.

## WinForms, ресурсы и совместимость

- Сохраняй совместимость WinForms Designer: partial-класс формы,
  `InitializeComponent`, поля контролов, ресурсы и существующие подписки событий.
  Меняй Designer-файлы только при необходимости для задачи; не переноси туда
  бизнес-логику и не удаляй обработчики без проверки всех ссылок.
- Обращайся к контролам из UI-потока через существующий механизм диспетчеризации.
  Не блокируй UI вызовами `.Wait()`/`.Result` для асинхронных операций.
  Учитывай закрытие формы, отмену задач и уничтожение контролов.
- Обрабатывай ошибки с полезной диагностикой. Освобождай соединения, потоки,
  таймеры, подписки и другие ресурсы; учитывай повторный запуск и остановку,
  многопоточность и завершение приложения.
- Сохраняй существующие форматы пакетов, кодировки, порядок байтов, команды,
  таймауты и поведение настроек, если задача явно не требует их изменения.
  Проверки с реальным оборудованием выполняй только в согласованном контексте;
  успешные модульные тесты не доказывают аппаратную совместимость.
- Не добавляй в репозиторий или журналы пароли, токены и другие секреты.
  Не публикуй пользовательские конфигурации и данные из среды выполнения.
- Сохраняй русские строки, кодировку файлов и существующие данные сценариев.
  Не возвращай удалённую упаковку установщика без запроса пользователя.

Установщик через Setup Project добавлен по запросу пользователя. Сохраняй его
тип `.vdproj`, публикацию через `Publish Items` и папку установки, доступную для
записи текущему пользователю. Не заменяй его другим упаковщиком без запроса.

## Проверки

Выполняй доступные проверки, соответствующие изменению. Для исправлений логики
используй существующие тесты и при необходимости добавляй регрессионный тест,
проверяющий поведение. Для правок документации не создавай искусственные тесты.

Полная сборка и выполнение тестов требуют Windows с .NET Framework 4.8 и .NET 9 SDK (компилятор C# 13). Из корня решения:

```powershell
dotnet restore MKtest.sln --verbosity minimal
dotnet build MKtest.sln --configuration Release --no-restore --verbosity minimal -p:ContinuousIntegrationBuild=true
dotnet test MKtest.Tests/MKtest.Tests.csproj --configuration Release --no-build --no-restore --verbosity normal --logger "trx;LogFileName=MKtest.Tests.trx"
git diff --check
```

Существующий CI: `.github/workflows/windows-build.yml`, runner `windows-2022`.
Он запускается при push в `master`, PR в `master` и вручную (`workflow_dispatch`).
Обычный push в другую ветку сам по себе этот workflow не запускает.
Установщик проверяется отдельным ручным workflow `.github/workflows/windows-setup.yml`:
сборка `.vdproj` через Visual Studio, установка, проверка файлов и ярлыков,
запуск и удаление. Не запускай `Test-Setup.ps1` поверх пользовательской установки.
CI Windows Server 2022 не подтверждает запуск на Windows 7 или установку самого Framework.
При проверке через GitHub Actions сверяй ветку и SHA, дождись результата и
проверь шаги сборки и тестов, а не только факт запуска workflow.

В Linux возможна кросс-компиляция с `-p:EnableWindowsTargeting=true` при наличии
SDK и пакетов, но она не заменяет запуск WinForms и тестов на Windows.
Не меняй целевую платформу проекта ради обхода ограничений среды.
Для изменений интерфейса дополнительно проверяй Designer, обработчики, раскладку
и закрытие формы на Windows; для протоколов указывай, проверялось ли оборудование.
Не коммить `bin/`, `obj/`, `TestResults/`, публикации и пакеты установщика.

## Git и отчёт

- Перед записью на GitHub проверяй целевой репозиторий и ветку. Не переключай
  основную ветку, не удаляй ветки и не переписывай историю без поручения пользователя.
- Перед разрешённым удалением ветки проверь, сохранены ли её коммиты в остающейся
  ветке; при наличии уникальных коммитов сообщи об этом до удаления.
- После записи проверь фактический результат на GitHub. Не утверждай, что GitHub
  обновлён, сборка успешна или код работает, без подтверждения.
- В итоговом отчёте указывай изменённые файлы, суть изменения, результат сборки и
  тестов, а также непроверенные функции. Если проверка недоступна или завершилась
  ошибкой, честно укажи ограничение и причину; не выдавай её за успешную.
